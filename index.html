About

LMML — Live Museum of Movie Locations (Seville) — is the end-of-course project developed by Sevda Rezaei Melal for the course “Information Modeling and Web Technologies”, taught by Prof. Fabio Vitali in the Master's degree in Digital Humanities and Digital Knowledge at the University of Bologna.

This interactive exhibition bridges the gap between fictional cinematic universes and the tangible architectural heritage of Seville. It reimagines the physical geography of the city through the lens of cinematic history, inviting users to experience urban space as a dynamic, living narrative.

The framework is repeatable by design: a JSON dataset systematically describes each location, its film shots, its adaptive texts, and narrative routings; this interface merely reads and dynamically renders it.

Furthermore, LMML employs a dual-narrative user interface designed to reflect different historical and cultural paradigms. Users can navigate the exhibition through distinct temporal lenses—ranging from the typographic constraints of early modern printing (1500–1800) to the bold, grid-based layouts of late 20th-century news media. This architectural choice is not merely decorative, but a deliberate method to contextualize the data.

01. Pre-design — Sketches and Browser Prototyping

Before the final code structure was established, the interface was conceptualized on paper and refined directly in the browser. The primary challenge was architectural: how to design a single layout skeleton that could simultaneously handle a complex JSON data matrix (2 narratives × 3 user personas × 3 text depths) and two radically different visual themes.

  • Hand-drawn sketches: Initial sketches focused purely on information flow and spatial hierarchy. They resolved the critical placement of the global Narrative themes alongside the internal Persona Tabs (Kids / Adults / Specialists). The objective was to ensure that the mechanics of the multi-dimensional matrix remained intuitive and accessible without cluttering the reading experience.
  • Direct Browser Prototyping: Bypassing intermediary design software, development moved directly from paper to HTML/CSS scaffolding. The browser served as the primary styling laboratory across standard desktop and mobile breakpoints. Instead of designing a single static look, I tested the exact same structural wireframe against two opposing visual paradigms to verify that the interface could seamlessly transition between the classical proportions of EB Garamond and the modernist asymmetry of Helvetica.
  • App-Like Viewport & Internal Scrolling: A crucial architectural decision was strictly disabling global body scrolling. The interface is engineered with a fixed viewport (utilizing 100vh and 100dvh), acting as a native application shell rather than a traditional webpage. Only specific content areas (like the text panels or this documentation view) are permitted to scroll internally. This ensures that critical navigation controls and Persona Tabs remain permanently pinned to the screen, providing uninterrupted access to the data matrix.
  • Progressive Disclosure & UI Decluttering: A major UX challenge was accommodating multiple JSON data controls without overwhelming first-time users. To reduce cognitive load, strict visual hierarchy and progressive disclosure were applied. Instead of displaying massive walls of text, secondary controls—such as the typography-driven "Read More" dropdowns—allow users to dig into detailed explanations on demand. By stripping away rigid borders and heavy bounding boxes, the interface avoids "button fatigue" and maintains an elegant, uncrowded aesthetic.

02. Multi-Dimensional Data Architecture & Matrix

Unlike traditional linear websites, this project employs a multi-dimensional content architecture. The data for each location is structured as a JSON matrix, separating the active storyline from the user's reading profile, while dynamically routing their physical journey.

  • The 6-Object Content Matrix with Progressive Depth (lmml:textMatrix): Content is not hardcoded into the HTML. Instead, the application fetches a JSON object containing a 6-object array for each location. This represents two parallel realities (Historical Timeline vs. Cinematic Fantasy) multiplied by three core personas (Kids / Adults / Specialists). However, within each object, the text is structured in three progressive depth levels (microText, summaryText, detailedText). When a user toggles a Persona Tab or clicks "Read More," JavaScript dynamically filters and reveals the precise string required, ensuring the interface never breaks the user's active context.
  • Dynamic State Routing (lmml:narrativeRouting): The application acts as a state machine rather than a simple hyperlinked site. The "Next Location" button does not have a static URL. Instead, the app consults the narrativeRouting array. If the user is immersed in the Historical narrative, the router strictly guides them to the next archaeological site (e.g., from Itálica to the Roman ruins). If they switch to the Cinematic narrative, the router seamlessly diverts their path to the next filming location (e.g., a Game of Thrones set).
  • Data Decoupling: By strictly separating the content (the JSON matrix) from the presentation (the HTML/CSS shell), the methodology remains highly stable and scalable. Adding a third narrative in the future would only require appending new objects to the matrix, with zero changes needed in the underlying JavaScript logic.

03. UX Design & Real Use Cases

To ensure the complex data matrix serves actual user needs rather than becoming a technical gimmick, the interface was designed around two distinct user personas. These scenarios demonstrate how the combination of Visual Themes, Narrative Contexts, Persona Tabs (Kids / Adults / Specialists), and Progressive Disclosure ("Read More") accommodates entirely different types of cultural tourism within the exact same application.

  • ◈ Persona A: The Academic Researcher
    Profile: A university student or historian visiting Itálica to study Roman urban development and Hadrianic architecture.
    Path through the site: They toggle the site to Theme I (Early Print) to reduce screen fatigue and simulate a historical archive. They choose the Historical Timeline narrative and select the Specialists Persona tab. Seeking deep analysis, they expand the "Read More" dropdown to access the full detailedText.
    Outcome: The interface filters out all pop-culture references. The user is presented with justified typography, classical drop caps, and advanced architectural data (e.g., dimensions of the fossa bestiaria), fully supported by academic citations without the distraction of cinematic tourism.

  • ◈ Persona B: The Cinematic Tourist
    Profile: A pop-culture fan traveling to Seville to trace the filming locations of Game of Thrones, seeking to compare the real ruins with screen VFX (Visual Effects).
    Path through the site: They switch to Theme II (Swiss Grid) for a modern, visual-heavy, magazine-style layout. They choose the Cinematic Fantasy narrative and select the Adults Persona tab. They consume the quick summaryText without needing to dig into heavy academic footnotes.
    Outcome: The application dynamically pivots. The text now reveals how the production designer utilized the ruins to create the Dragonpit. The layout shifts to flush-left reading, allowing the tourist to stand in the exact spot the dragons landed while reading accessible, engaging behind-the-scenes facts.

04. Visual Design System & Themes

The project requires the interface to act not just as a container, but as a storytelling device itself. Both themes run on a single CSS architecture where colors, fonts, and grid behaviors are stored as CSS variables on :root. The themes are toggled via a [data-theme] attribute, and the user's choice is saved in localStorage to ensure persistence.

Theme I — 1500–1800 (Early Print & Renaissance)

Inspired by the transition from illuminated manuscripts to mechanical movable type, this theme reflects the aesthetics of the hand-press period. It is designed for deep, immersive reading of historical narratives.

  • Palette: Warm rag paper (ivory/beige backgrounds) to avoid the harshness of pure white, paired with natural iron gall ink colors.
  • Typography: A humanist old-style typeface (EB Garamond) mimicking the organic stroke of a broad-nib pen.
  • Layout Signature: Typography prioritizes historical accuracy with single solid rules, prominent red oxblood drop capitals (Rubrication), and text alignments that lean towards justification. Emphasis relies strictly on italicized highlights rather than bold weights.

Theme II — Second Half of the XX Century (Swiss Design)

This theme abandons historical classicism for the International Typographic Style, reflecting post-war modernism and industrial magazine spreads. It provides a modern, objective framing perfect for cinematic narratives.

  • Palette: Coated white stock (pure backgrounds), unvarying industrial black text, and one sharp Swiss-red accent to establish hierarchy.
  • Typography: Neo-grotesque type (Helvetica/Univers), served as genuine system fonts to maintain functional purity and neutrality.
  • Layout Signature: Flush-left, rag-right setting (abandoning justification), an asymmetric grid with the photograph bleeding full height, and the metadata structured as a rail closed by heavy rules.

05. Technical Architecture

The project is engineered as a Single Page Application (SPA) using purely Vanilla HTML, CSS, and JavaScript. There are no build tools (like Webpack), no heavy frameworks (like React or Vue), and no server-side dependencies. This ensures maximum archival longevity, portability, and readability—core principles for Digital Humanities projects.

File Structure

The application follows a strict decoupling of content (JSON), presentation (CSS), and logic (JS):


/LMML-Project
├── index.html        ← Landing / Cover page
├── explore.html      ← The core SPA (Renderer)
├── docs.html         ← Documentation (This page)
├── css/
│   └── style.css     ← Unified Design System & Theme Tokens
├── js/
│   └── app.js        ← State management, matrix routing, and DOM manipulation
└── data/
    ├── loc_01.json   ← JSON-LD matrix (Itálica)
    └── loc_02.json   ← JSON-LD matrix (Real Alcázar)

CSS Architecture: The Theme Engine

The entire visual duality of the site is controlled through a centralized CSS token system. Colors, typography, and spacing are defined as custom properties (CSS variables) on the :root pseudo-class. When the user switches themes, JavaScript simply toggles a [data-theme="late-xx-century"] attribute on the <body> tag. This approach cascades the new variables down the DOM, instantly re-rendering the entire UI from Early Print to Swiss Design without writing duplicate CSS classes.

State Management & Persistence

To create a seamless SPA experience, the application must "remember" user preferences. I utilized the browser's native localStorage API to preserve the state across page reloads and physical locations. The application tracks and saves:

  • Theme Preference: (e.g., early-print or late-xx-century)
  • Active Narrative: (e.g., narrative_1_historical vs. narrative_2_epic)
  • Active Persona: The specific user profile selected from the UI tabs (Kids, Adults, or Specialists), which maps directly to the backend matrix values (e.g., intro + young).

Whenever a user interacts with the themes or Persona Tabs, JavaScript updates both the DOM and the localStorage object simultaneously, ensuring the environment remains strictly tailored to their choices as they navigate from loc_01 to the next destination.

06. Metadata Model & JSON-LD

In Digital Humanities, content must be as legible to machines as it is to humans. The core of the LMML architecture is its Linked Data model, embedded as application/ld+json within the files. However, representing a multi-dimensional matrix (narrative paths × personas × text depths) required extending standard semantic vocabularies with a project-specific ontology.

Standard Vocabularies: Schema.org

Wherever possible, the data model relies on established semantic web standards to ensure interoperability. The overarching location data is structured using standard entities like schema:Place. Within the matrix itself, each distinct text block is typed as a schema:CreativeWork, and academic references are mapped using schema:citation.

The Project Namespace (lmml:*)

While Schema.org is excellent for general metadata, it lacks the specialized fields required for our multi-dimensional Matrix UI. To bridge this gap, I designed a custom namespace (lmml:) to control the application's logic directly from the metadata:

  • lmml:textMatrix: The container array holding the 6 distinct persona variations for a single location.
  • lmml:targetNarrative: Binds a specific text block to the global Narrative context (e.g., narrative_1_historical vs. narrative_2_epic).
  • lmml:competence & lmml:tone: Categorizes the persona targeting, mapping the backend logic (e.g., intro+young or adv+scholar) directly to the UI's Kids, Adults, and Specialists tabs.
  • lmml:microText, lmml:summaryText, lmml:detailedText: Controls the progressive disclosure of information. This enables the UI's "Read More" interactions to unfold textual depth dynamically from a single JSON object.

Data Snippet Example

Here is how standard and custom vocabularies interlock within a single matrix cell to feed the UI:


{
  "@type": "schema:CreativeWork",
  "@id": "#txt_long_adv_scholar_hist",

  "lmml:tone": "scholar",

  "lmml:summaryText": "The Real Fábrica de Tabacos is the Enlightenment's answer...",
  "lmml:detailedText": "The result was commonly ranked the largest building...",

    { "@id": "#src_gordillo" }
  ]

07. Authorship & AI Disclosure

This project serves as an open ledger of intellectual labor. The following section clarifies the strict boundaries between original human authorship and the utilization of Large Language Models (LLMs) as technical assistants.

What I Created (Human Authorship)

The core intellectual, narrative, and architectural decisions of this project are strictly my own. I did not use AI to generate the substance of the museum:

  • The Core Concept & Methodology: Designing the "Live Museum" concept, the dual-theme UI (Early Print vs. Swiss Design), and the multi-dimensional Matrix reading experience.
  • Data Curation & Research: Selecting all physical locations (e.g., Universidad de Sevilla, Itálica), researching their historical significance (using sources like IAPH and Gordillo), and curating their cinematic counterparts (e.g., Carmen, Game of Thrones).
  • Narrative Writing: Authoring the specific text blocks for each location tailored to distinct user personas (Kids, Adults, Specialists) and structuring them across three progressive depths (micro, summary, and detailed). The tone, academic rigor, and stylistic shifts in the writing are my original work.
  • Visual Design & UX: Creating the paper wireframes, defining the typography (EB Garamond and Helvetica), choosing the color palettes (Iron Gall Ink, Swiss-red), and defining the Persona UX logic.
  • Data Architecture: Engineering the logic behind lmml:textMatrix and lmml:narrativeRouting.

How the LLM (AI Assistant) Was Used

The LLM was strictly employed as a syntax compiler and technical co-pilot to translate my logic into valid code:

  • JSON-LD Syntax Formatting: Once I mapped out the ontological structure and provided the raw text/data (e.g., coordinates, citations, camera angles), the LLM assisted in formatting this into valid, machine-readable JSON-LD syntax, ensuring proper nesting of schema:CreativeWork and my custom lmml:* namespaces.
  • JavaScript Logic Scaffolding: I described the required UX behavior (e.g., "The site must read the active narrative and persona from localStorage and filter the JSON matrix to reveal the correct progressive text"). The LLM provided the vanilla JS functions and CustomEvents required to manipulate the DOM without a framework.
  • CSS Troubleshooting: The LLM assisted in refining specific CSS media queries and flexbox/grid alignments to ensure the layout matched my structural sketches across mobile and desktop breakpoints.
